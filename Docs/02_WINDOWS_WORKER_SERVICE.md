# 02 — Windows Background Worker Service Specification

**Document purpose**  
Complete implementation contract for the .NET 8 Windows Background Worker Service only.  

This service runs on every monitored endpoint (staff laptops, desktops, internal servers). It is responsible for USB detection, event-log reading, session reconstruction, explainable risk scoring, offline buffering, and shipping structured data to the central API.

Agents implementing the Worker Service must also read:
- `01_PROJECT_OVERVIEW_AND_ARCHITECTURE.md` (architecture & non-negotiable principles)
- `03_BACKEND_API.md` (exact payload shape the API expects and authentication method)

## 1. Technology & Hosting

| Item | Choice |
|------|--------|
| Runtime | .NET 8 |
| Template | Worker Service |
| Installation | Windows Service (`sc.exe` or MSI) |
| Privileges | Least-privilege dedicated account (prefer **not** LocalSystem) |
| Configuration | `appsettings.json` + environment variables / User Secrets |

### Required configuration keys

```json
{
  "CorpCode": "ACME-UK-001",
  "ApiBaseUrl": "https://api.example.com",
  "ApiKey": "<service-to-api shared secret or client credentials>",
  "OfflineQueuePath": "C:\\ProgramData\\UsbDetector\\queue",
  "PollingIntervalSeconds": 5,
  "MaxBatchSize": 50,
  "EnableVerboseLogging": false
}
```

- `CorpCode` is mandatory. Every payload must carry it.
- Secrets must never be committed to source control.

## 2. Core Responsibilities

### 2.1 USB presence detection
- Continuously monitor for removable storage devices.
- Preferred methods: WMI (`Win32_DiskDrive`, `Win32_Volume`, `Win32_USBControllerDevice`) and/or relevant Event Log channels.
- Intensive event-log processing starts **only** when a USB device is present (or within a short cool-down window after removal).

### 2.2 Audit-policy awareness (mandatory behaviour)
On USB insertion the service **must**:

1. Query the current state of:
   - Audit PNP Activity
   - Audit Removable Storage
2. If either setting is **disabled**, generate a high-severity alert with the reason:  
   `"Required audit settings are disabled – file-level detection incomplete"`.
3. **Never** attempt to enable or modify Windows audit policies automatically.

Rationale: changing audit policy is a privileged organisational decision. Many enterprises will reject a product that modifies Local Security Policy without explicit administrator consent.

### 2.3 Event log reading
Only while a USB device is connected (or shortly after), read the relevant channels. Key Event IDs include (non-exhaustive):

| Event ID | Meaning |
|----------|---------|
| 6416 | New external device recognised |
| 4663 / 4656 | Object access (file read/write) on removable volumes |
| Partition / Diagnostic events | Device arrival / removal |
| DriverFrameworks-UserMode events | Additional PnP lifecycle |

The service must tolerate missing channels or events gracefully.

### 2.4 Session reconstruction
Group related events into logical USB sessions:

- Device arrival
- Series of file operations (if audit settings allow)
- Device removal (clean or abrupt)

Each session receives a unique `SessionId` (GUID generated by the service).

### 2.5 Explainable risk scoring
Apply a small set of weighted, human-readable rules. Examples:

- Large volume of data written
- Activity outside normal working hours
- Device serial not present in the organisation’s Allowed Devices list (the service may receive a cached list from the API or work with a local copy)
- User is marked as a leaver / high-risk
- Abrupt removal without clean eject

**Every rule that fires must produce a reason object containing:**
- Rule name
- Weight
- Human-readable description
- List of concrete Event Record IDs that triggered it

The overall `RiskScore` is the sum (or capped sum) of the weights of fired rules.

### 2.6 Host context
Every outbound payload must include:

- `HostName`
- Machine / Device GUID
- Currently logged-on interactive user(s)
- OS version
- `CorpCode`
- UTC timestamp

### 2.7 Offline resilience (non-negotiable)
- Persist every generated payload to a local durable store **before** attempting network transmission.
- Preferred store: SQLite. Acceptable alternative: append-only JSON / binary files in `OfflineQueuePath`.
- When the central API is reachable, drain the queue in FIFO order and mark items as delivered.
- Never discard events because the host is offline or the API is temporarily unavailable.
- Implement exponential back-off for network failures.

### 2.8 Outbound communication
- HTTPS POST of JSON batches to the central API (`/api/ingest/batch` or equivalent).
- Authenticate with the configured `ApiKey` or client-credentials grant.
- Support configurable batch size (`MaxBatchSize`).

## 4. Operational Behaviour Summary

| Situation | Required behaviour |
|-----------|--------------------|
| USB inserted | Start monitoring, check audit settings, begin session |
| Required audit settings missing | Raise high-severity alert, continue with best-effort detection |
| File writes occur (audit on) | Capture 4663/4656 events, update session volume & risk |
| USB removed | Close session, finalise risk score, queue payload |
| Network unavailable | Persist to local queue, keep collecting |
| Network restored | Drain queue in order, mark delivered |
| Service starts | Recover any undelivered items from the local queue |

---

## 5. Security Requirements Specific to the Worker

- Run under a least-privilege Windows account.
- Never store secrets in plain text inside the binary.
- Protect the offline queue directory with appropriate ACLs.
- Do not elevate privileges or modify system policy.
- Log security-relevant actions (start, stop, failed auth to API, queue overflow) without writing sensitive data.

---

## 6. Implementation Order Recommendation

1. Project scaffolding + Windows Service installation
2. Configuration loading (`CorpCode`, API URL, queue path)
3. USB presence detection (WMI or event-based)
4. Audit-policy status check
5. Basic event-log reading for device connect/disconnect
6. Local durable queue (SQLite recommended)
7. Session reconstruction + risk-scoring engine with reasons
8. HTTPS client + batch upload + retry logic
9. Full offline ↔ online cycle testing
